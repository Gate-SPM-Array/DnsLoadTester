DNS Load Tester – user and technical guide

A utility for measuring over time (minutes, hours or days) the capacity of a DNS server to answer queries, with a real-time dashboard and complete recording to disk. This guide describes every element of the interface and, for each one, the technical rationale: what it measures, why it is designed that way and how to interpret it.

1. Purpose and principles

The program generates a controlled stream of DNS queries towards a server, measures the outcome and latency of each one, aggregates the results per second and per minute and continuously assesses the state of the server (OK, degraded, unavailable). It is designed primarily for external authoritative servers, but it also works against recursive resolvers.

Design principles, useful for understanding everything else:

  • Fixed-rate load (open loop). Queries are sent according to a predetermined time grid (for example one every 50 ms at 20 qps), regardless of how quickly the server responds. This is the correct way to observe degradation: if the rate depended on the responses, a slow server would receive less load and would look better than it is.
  • No data lost. Every completed query is recorded on disk; aggregates and events are written and flushed to disk every second. A crash, a power cut or a forced close does not erase what has already been measured.
  • Exact percentiles per interval. Latencies are collected in histograms; the percentiles of a minute or of the whole session are computed over the full set of queries, not as the average of the per-second percentiles (which would be mathematically incorrect).
  • Measured from the client's point of view. Latency is the time from sending to receiving the complete response, measured on the test machine: it includes the network path. This is what a real resolver querying the server from that network experiences.
AuthorisationUse the program only against your own servers or with the written authorisation of the owner. Even a moderate load, sustained for hours against third-party infrastructure, may be interpreted as an attack and trigger countermeasures or reports.

Interface language

The program speaks Italian and English. On first start the language follows that of Windows (Italian if Windows is in Italian, otherwise English); it is changed with the 🌐 Language button in the command bar. The choice is saved and applied at restart, which the program offers straight away (during a test it is only stored). The interface, messages, events and HTML report are translated; the headers and values of the CSV files (for example the health column) and the states saved in summary.json stay unchanged, so as not to break anything that processes them.

The translations are readable JSON files: the Italian text written in the code is the key, the translation is the value ("Avvia test": "Start test"). To correct the English or add a language, all you need is a lang\<code>.json file next to the executable (menu 🌐 → Open the translations folder): missing texts stay in Italian, and a translation that alters the {0} placeholders is ignored. It is the same scheme used by the author's other projects (AdbSync, Pietrasanta Traceroute GUI).

SmartScreenThe executable is not digitally signed: on first start Windows may show “Windows protected your PC”. Choose “More info” → “Run anyway”.

5. Configuration panel

All values are saved automatically when each test starts and presented again the next time the program opens. Numeric fields accept whole numbers only, except the percentage thresholds (which also accept decimals).

5.1 Target

ElementPurpose and technical rationale
Protocol UDP (RFC 1035): the normal DNS transport, one query per datagram; it is what the vast majority of resolvers use towards authoritative servers.
TCP (RFC 7766): mandatory for large responses (truncated over UDP) and for zone transfers; an authoritative server must also answer over TCP.
DoT – DNS over TLS (RFC 7858), port 853: DNS over an encrypted TCP connection.
DoH – DNS over HTTPS (RFC 8484): DNS inside HTTPS requests; used by browsers and operating systems.
DoQ – DNS over QUIC (RFC 9250), port 853 UDP: encrypted like DoT, but without TCP's head-of-line blocking.
When the protocol is changed, the port switches to the standard value (53, 853 or 443) if it was set to one of these.
ServerIPv4 or IPv6 address or name of the server. The field is an editable box with history: the arrow shows the last 30 values used, and typing gives auto-completion. A value enters the history only when it is actually used (start of a test or successful check).
If a name is given, it is resolved once only at startup with the system resolver, and that address is used for the whole session: the measurement thus always concerns the same node, even if the name has several.
⋯ (history)Menu to remove the current entry from the history, clear the history of that field, or clear the whole history (servers, URLs, TLS names).
PortPort of the service: 53 for UDP/TCP, 853 for DoT/DoQ.
IP familyUsed only if the server is given by name. Automatic IP prefers IPv4 if available; IPv4 only / IPv6 only force the family. Useful for comparing the two ways of reaching the same server, which often have different network paths.
DoH URLDoH only: full URL of the service (e.g. https://dns.example.com/dns-query), with history like the Server field. The name in the URL is resolved by the system at every new HTTP connection. The system proxy is ignored: the measurement must concern the server, not an intermediate proxy.
POST / GET methodPOST sends the DNS message in the body (application/dns-message); GET encodes it in base64url in the ?dns= parameter. GET can be stored in HTTP caches: for this reason RFC 8484 recommends ID = 0, and the program always uses ID 0 in DoH.
HTTP versionHTTP/1.1: one request at a time per connection. HTTP/2: several simultaneous requests on the same connection (multiplexing); this is the most common case. HTTP/3: HTTP over QUIC (requires Windows 11 / Server 2022). The version is exact: if the server does not support it, the query fails instead of falling back to another version, so the test measures what was requested.
TLS name (SNI)DoT and DoQ only: the name the server certificate must contain, sent in the SNI extension. Empty = same as the Server field. Essential when the server is given by IP but the certificate carries a name. It has a history.
Do not verify the server certificateTurns off certificate checking (chain, expiry, name). It is only for the lab or with internal certificates: in a real test an invalid certificate is a problem to report, not to work around.
Reuse connectionsNot present for UDP. On (default): each worker keeps its own TCP/TLS/QUIC/HTTP connection and reuses it, as a real resolver does. Off: a new connection for every query, so the latency includes the handshake (TCP and TLS) every time. Comparing the two cases measures the cost of the handshake and the server's ability to accept new connections.
If the server closes an idle connection, the program reopens it transparently with a single new attempt, without counting it as an error.

5.2 Queries

ElementPurpose and technical rationale
Query listOne query per line, in the form name TYPE (e.g. example.com SOA). Also accepted are TYPE name, the CSV format name,TYPE and name alone (the default type is used). Empty lines and lines starting with # or ; are ignored. Internationalised names (with accents) are automatically converted to punycode. Invalid lines are discarded with a warning, visible in the events.
{rnd}Placeholder replaced at every query by 10 random characters [a-z0-9], for example {rnd}.example.com → k8dm1c75ls.example.com. Every name is different, so no intermediate cache can answer: on an authoritative server it tests the generation of NXDOMAIN responses; on a recursive resolver it forces the authoritative servers to be queried at every query. It is also the technique used in “random subdomain” (water torture) attacks: use it sparingly and only with authorisation.
Load…Loads the list from a .txt or .csv file (replaces the content). Above 200,000 lines confirmation is requested.
Save…Saves the current list to a UTF-8 text file. If the list comes from a loaded file, it proposes the same name with an incremented version (_v1.0 → _v1.1); otherwise it proposes query_<label or server>_v1.0.txt.
Default typeRecord type for lines without a type. It can be chosen from the list or any known type can be typed, or TYPEnnn / a number for types not in the list (RFC 3597).
Query orderSequential: queries follow one another cyclically in the order of the list, a perfectly uniform distribution. Random: each query is drawn at random; it better simulates real traffic and avoids repetitive patterns that some rate-limiting mechanisms recognise.
RD flagRecursion Desired. Off (default): like a resolver querying an authoritative server; it is the correct setting for testing an authoritative server. On: requests recursive resolution, essential for testing a resolver. Many resolvers answer REFUSED to queries without RD (protection against “cache snooping”). A well-configured authoritative server, on the other hand, answers only for its own zones even with RD on: if it resolved third-party names it would be an open resolver, exploitable for amplification attacks.
EDNS0 + bufferAdds the OPT record (RFC 6891) and advertises the maximum UDP response size accepted. The recommended value is 1232 bytes (DNS Flag Day 2020): it avoids IP fragmentation, a frequent cause of lost responses. Without EDNS, UDP responses are limited to 512 bytes and larger ones arrive truncated (TC flag). With EDNS the program also interprets the extended RCODE and Extended DNS Errors.
DNSSEC (DO)Sets the DNSSEC OK bit: the server includes the signatures (RRSIG) in the responses for signed zones. The responses become much larger: it is a good load test for bandwidth and fragmentation, and it checks that the server serves DNSSEC records correctly.

5.3 Load and duration

ElementPurpose and technical rationale
Target QPSTotal queries per second to send. Queries are distributed evenly over an absolute time grid (query n at instant n/QPS), not in bursts. 0 = no limit: each worker sends the next query as soon as it receives the response (maximum throughput test, to be used with extreme caution against external servers).
WorkersNumber of queries “in flight” at the same time (from 1 to 5000). Each worker has a single channel (socket or connection) and a single query at a time. By Little's law at least QPS × mean latency workers are needed to sustain the rate under normal conditions, but to maintain it even when the server does not respond (every query waits for the timeout) QPS × timeout are needed. Example: 200 qps with a 2 s timeout → 400 workers. With fewer workers, during an outage the load sent drops by itself (visible in the “Sent/s” line): the Warnings box flags this.
Timeout (ms)Maximum wait for a response (from 50 to 60,000 ms), beyond which the query is counted as TIMEOUT. Real resolvers typically wait between 400 ms and 2 s before retrying or moving to another name server: a value in this range makes the test realistic. A query that times out is counted in the second in which the timeout expires.
Ramp-up (s)Duration of the gradual increase: the rate grows linearly from zero to the target QPS. It avoids hitting the server with the full load from cold (caches, connections, any anti-DDoS systems) and makes it possible to observe at which level problems begin.
DurationDays, hours and minutes. When it expires the test stops in an orderly way and generates the report.
No time limitThe test continues until Stop is pressed or the program is closed.
Why a fixed time gridIf the program falls behind (slow server or insufficient workers), the queries not sent on time are not made up with a burst: beyond 1 second of delay the grid is realigned. A catch-up burst would distort the measurement at the worst possible moment. Instead, the delay becomes visible: the “Sent/s” line drops below the target. This is the behaviour that avoids the methodological error known as coordinated omission.

5.4 Server state assessment

Every second the program assesses the queries completed within a sliding window and assigns a state. The same criteria feed the “Server state” indicator, the coloured strip in the report, the health column of the aggregates and the events.

ElementPurpose
Observation window (s)Number of seconds considered (from 1 to 300, default 10). Short windows react immediately but are “jumpy”; long windows are stable but report later.
Degraded if success below (%)Default 99%: more than 1 query in 100 without a valid response in the window brings the state to DEGRADED.
… or p95 latency above (ms)Default 500 ms: even with all responses received, if the slowest 5% exceed the threshold the state is DEGRADED. Slow responses are almost equivalent to lost responses, because resolvers time out and retry.
Unavailable if success below (%)Default 50%. The state is UNAVAILABLE also when queries were sent in the window and none was completed. It must be lower than the degraded threshold.
NXDOMAIN validIf on (default), NXDOMAIN is a correct response: the server answered that the name does not exist, and it is the expected response for {rnd} queries. Turn it off only if all the names in the list must exist.
HysteresisA deterioration is reported immediately; an improvement only after the new state has remained stable for as many seconds as the window. This way a single good second during an outage does not produce a burst of alternating OK/UNAVAILABLE events. An episode is counted every time the state goes from OK (or no data) to DEGRADED or UNAVAILABLE.

“Success” means a NOERROR response (including responses without records, known as NODATA), plus NXDOMAIN if the option is on. SERVFAIL, REFUSED, the other RCODEs, timeouts and transport errors are failures.

5.5 Logs and export

ElementPurpose and technical rationale
FolderFolder in which a subfolder is created for each session, named YYYYMMDD_hhmmss_PROTOCOL_server[_label]. The “…” button opens the folder picker.
Session labelOptional text added to the folder name (customer, ticket, scenario). It makes it easier to sort many sessions.
Per-query logAll queries: one line for every query (maximum forensic detail). Failures only: records only timeouts, errors and invalid responses; suitable for multi-day tests at a high rate. Off: aggregates and events only. In all cases the per-second and per-minute aggregates remain complete.
File rotation (MB)Size beyond which the per-query log moves on to a new file (queries_0001.csv, queries_0002.csv, …). Files of a few hundred MB remain manageable with Excel, editors and analysis tools.
CSV formatExcel Italian: ; separator and decimal comma; opens with a double-click in Excel configured in Italian. Standard: , separator and decimal point (RFC 4180), for Python, Power BI, SIEM. The format applies to all the CSV files of the session and is recorded in session.json, so the report reads them back correctly.

The per-query log takes about 110 bytes per query: for example 100 qps for 7 days ≈ 6.7 GB.

5.6 Warnings

The yellow box at the bottom of the configuration updates as values are changed and flags situations that are not blocking but are important:

  • Insufficient workers: with the number of workers given, if the server stops responding the load would drop to about workers ÷ timeout qps. The minimum number needed to maintain the target is shown.
  • Unlimited QPS: a reminder about responsible use.
  • Disk space: estimate of the per-query log when above 2 GB.
  • Certificate not verified.

The same warnings appear in the start confirmation window.

Many servers attach to their responses a code explaining the reason for the refusal or the error. The program decodes it and shows it in the Detail column, for example EDE 18 Prohibited (refusal by policy), EDE 20 Not Authoritative, EDE 6 DNSSEC Bogus, EDE 22 No Reachable Authority, EDE 15 Blocked, EDE 3 Stale Answer. The detail also appears in the main errors table of the report.

9. Measurement methodology

Load generation

  • Workers: each has its own channel (“connected” UDP socket, TCP/TLS connection, QUIC connection or shared HTTP client for DoH) and one query at a time. This isolates the workers from one another and makes the concurrency exactly what was configured.
  • Scheduler: send instant of query n = n / QPS from the start (with the ramp-up, a curve that makes the rate grow linearly). If sending is more than 1 s late, the grid is realigned instead of catching up with a burst.
  • During the test Windows does not go into automatic sleep, and the system timer resolution is set to 1 ms, for a regular cadence even at a few qps.

Query construction and validation

  • Random ID for each query over UDP, TCP and DoT; ID 0 in DoH and DoQ, as required by RFCs 8484 and 9250.
  • Class IN; RD flag according to the configuration (CD always 0); OPT record if EDNS is on (buffer and DO bit configurable).
  • A response is accepted only if it has the QR bit, the same ID and the same question section as the query (case-insensitive comparison). This is the same check a resolver performs to defend itself against spoofed responses: it guarantees that every response counted really is the one for the query being measured.
  • Over UDP, responses with a different ID are discarded and the program keeps waiting for the right one until the timeout (late responses).
  • Over TCP/DoT, after a timeout the connection is closed and reopened (the state of the stream is no longer reliable).
  • In DoQ each query uses a new bidirectional stream on the worker's QUIC connection (ALPN doq, maximum idle time 30 s).

Latency measurement

  • High-resolution stopwatch started immediately before sending and stopped on complete receipt of the response.
  • If a connection has to be opened for that query (a worker's first send, connection closed by the server, reuse off), the latency includes the TCP/TLS/QUIC handshake, as happens to a real client.
  • Latencies are collected in a log-linear histogram: 1 µs resolution up to 64 µs, then 32 buckets for each doubling, with a maximum relative error of around 3% over the whole scale up to tens of seconds. The percentiles for the second, minute, window and session are computed from the histogram of the corresponding set.

Aggregation

  • Each result is attributed to the second in which the query concludes. Each closed second produces a line in intervals_1s.csv; every 60 seconds a line in intervals_1m.csv.
  • Statistics are processed by a single dedicated thread, separate from the workers: the send path has no locks and the measurement is not disturbed by the processing.
  • If the PC remains frozen or asleep for more than an hour, the missing interval is not filled with empty seconds: a “time jump” event is recorded.

11. Reports and after-the-fact analysis

HTML report

Generated automatically at the end of every test, it is a self-contained HTML file (it opens in any browser and can be printed to PDF with Ctrl+P → “Save as PDF”). It contains:

  • a summary with a verdict (green, yellow or red) and the main indicators, including availability (seconds not “unavailable” out of the seconds measured);
  • a strip showing the health state over time, and throughput, latency and failure charts;
  • the latency distribution by band;
  • tables of outcomes, overall latencies (min, mean, p50, p90, p95, p99, p99.9, max), availability by state, other indicators, main errors, results per query;
  • significant events, the complete test configuration and the list of session files.

For long tests the report charts use the per-minute data and at most 1500 points: in merged points the QPS is the average, p50 the average, and p95, p99 and maximum are the worst value in the group, so peaks remain visible.

Open session…

Loads a saved session into the dashboard, even one from other PCs or one that was interrupted. The charts are rebuilt from intervals_1s.csv and intervals_1m.csv (streamed reading: even multi-day sessions open in a few seconds) and are fully navigable; indicators, outcomes and results per query come from summary.json, the events from events.csv. A session cannot be opened while a test is running.

12. Recommended test scenarios

Authoritative server

  1. Reconnaissance. Identify the name servers of the zone (NS records) and their addresses. Check whether they are on different networks: RFC 2182 recommends distributing them, so that a network failure does not hit them all at once.
  2. Consistency. With “Check target”, query zone SOA on each name server: the serial number must match, otherwise the secondaries are not synchronising. Also compare NS, MX and the main records.
  3. Protocols. Repeat the check over TCP (it must work), without EDNS (responses limited to 512 bytes, possible TC) and with DNSSEC (DO) if the zone is signed.
  4. Availability over time. A list with only names from the hosted zones plus {rnd}.zone A, RD flag off, low load (2–20 qps), duration 24–72 hours. To compare several name servers, run several instances of the program in parallel, one per server: you can see straight away whether the degradations are common (shared network) or affect a single node.
  5. Step capacity (only with formal authorisation). 10-minute sessions at increasing load (e.g. 10, 50, 100, 200 qps) with ramp-up. Note the level at which p95/p99 rise or timeouts and truncated responses appear.

Recursive resolver

  • RD flag on, list of real domains in random order, NXDOMAIN valid.
  • The first pass fills the cache: from then on the latencies mainly measure responses from the cache. To measure full resolution use {rnd} names (sparingly: each one generates traffic towards the authoritative servers of that domain).

Encrypted services (DoT, DoH, DoQ)

  • Compare connection reuse on and off to measure the cost of the handshake and the ability to accept new connections.
  • In DoH compare HTTP/1.1, HTTP/2 and HTTP/3 and the GET and POST methods.

13. How to read the results

What you observeLikely interpretation
Sent/s below the targetThe client cannot keep up with the rate: workers insufficient for the latency or timeout. It is not a server limit: increase the workers.
Responses/s below Sent/s, timeouts increasingThe server (or the network) is losing queries. If this happens above a certain load threshold and is proportional to the load, it is a capacity limit or a rate-limiting mechanism.
Timeouts in regular spikes (every N minutes)Periodic activity on the server or the network: zone reloads, backups, log rotation, route changes. Compare the times with the server logs.
Stable p50, p95/p99 spikingMomentary queues on the server or network jitter. If the spikes coincide with those of several name servers on different networks, the cause is probably close to the test machine.
All latencies rise togetherSaturation (CPU, bandwidth, network queue) or a change of network route.
Responses with the TC flag, or timeouts on some queries onlyResponse Rate Limiting (RRL): the authoritative server limits responses per source address and truncates or drops the excess. It hits identical repeated responses first: compare a list with a single name and one with many different names.
SERVFAIL on an authoritative serverZone not loaded, DNSSEC signing error, failed server backend. Check the EDE detail and the “Per query” tab.
REFUSEDZone not hosted, RD not allowed, ACL. See the suggestion in Check target.
Connections growing continuouslyThe server is closing the connections (idle time or limit on queries per connection): legitimate behaviour, but every reopening costs a handshake.

14. Limitations and caveats

  • A single source address. All traffic leaves from the test machine. Per-IP-address protections (RRL, firewalls, anti-DDoS) kick in well before the server's real capacity: the limit measured from a single PC is often that of the protection. Measuring the real capacity requires several machines or a test agreed with the operator.
  • The measurement includes the network. Latencies and losses include the path between the machine and the server. To distinguish server problems from network problems, compare several name servers and, if possible, several measurement points.
  • Anycast. If the server is anycast, you measure the node reached by the test machine, not the whole service.
  • Capacity of the test PC. At very high rates (thousands of qps) the limit may become the PC's CPU or network: check “Sent/s” and the “queue” in the status bar.
  • Name resolution. The server name is resolved once at startup: a change of address during the test is not followed.
  • Windows updates. The program prevents sleep, but not scheduled restarts: turn them off for the duration of long tests.

15. Troubleshooting

SymptomCause and remedy
All responses REFUSEDResolver queried without RD → turn on “RD flag”. Authoritative server queried for zones it does not host → use names from its zones. REFUSED even with RD on → source address not authorised (ACL).
All queries TIMEOUTPort filtered by a firewall (local, corporate or the server's), wrong address, protocol not offered (e.g. DoT not enabled). Try UDP and TCP on port 53 for comparison.
NET_ERROR “ConnectionReset” over UDPThe server replied “port unreachable” (ICMP): no DNS service at that address and port.
TLS_ERRORCertificate not trusted or with a different name: set the correct “TLS name (SNI)”. Only in the lab, turn off verification.
HTTP_ERROR 404/415 in DoHWrong URL path (often /dns-query) or method not supported: try the other method.
“QUIC not supported”DoQ and HTTP/3 require Windows 11 or Windows Server 2022 or later and msquic.dll next to the executable.
Many “late responses”Timeout too short compared with the server's real latency: increase it.
Queue growing in the status barThe PC cannot process the results at the required rate: reduce the QPS or the per-query log (“Failures only”).
Unexpected interface errorThe test continues and the data stays saved. Send the crash.log file from the data folder for diagnosis.
