DNS Load Tester – guida d'uso e tecnica

Utility per misurare nel tempo (minuti, ore o giorni) la capacità di un server DNS di rispondere alle query, con cruscotto in tempo reale e registrazione completa su disco. Questa guida descrive ogni elemento dell'interfaccia e, per ciascuno, il razionale tecnico: cosa misura, perché è fatto così e come interpretarlo.

1. Scopo e principi

Il programma genera un flusso controllato di query DNS verso un server, misura per ognuna esito e latenza, aggrega i risultati al secondo e al minuto e valuta continuamente lo stato del server (OK, degradato, non disponibile). È pensato in primo luogo per server autoritativi esterni, ma funziona anche verso resolver ricorsivi.

Principi di progetto, utili per capire tutto il resto:

  • Carico a ritmo fisso (open loop). Le query partono secondo una griglia temporale prestabilita (ad esempio una ogni 50 ms a 20 qps), indipendentemente da quanto rapidamente risponde il server. È il modo corretto per osservare la degradazione: se il ritmo dipendesse dalle risposte, un server lento riceverebbe meno carico e sembrerebbe migliore di quanto è.
  • Nessun dato perso. Ogni query completata è registrata su disco; aggregati ed eventi sono scritti e svuotati sul disco ogni secondo. Un crash, un blackout o la chiusura forzata non cancellano ciò che è già stato misurato.
  • Percentili esatti per intervallo. Le latenze sono raccolte in istogrammi; i percentili del minuto o dell'intera sessione sono calcolati sull'insieme delle query, non come media dei percentili dei secondi (che sarebbe matematicamente scorretta).
  • Misura dal punto di vista del client. La latenza è il tempo dall'invio alla ricezione completa della risposta, misurato sulla postazione di prova: comprende il percorso di rete. È ciò che percepisce un resolver reale che interroga il server da quella rete.
AutorizzazioneUsare il programma solo verso server propri o con autorizzazione scritta del titolare. Anche un carico moderato, protratto per ore verso un'infrastruttura di terzi, può essere interpretato come un attacco e attivare contromisure o segnalazioni.

Lingua dell'interfaccia

Il programma parla italiano e inglese. Al primo avvio la lingua segue quella di Windows (italiano se Windows è in italiano, altrimenti inglese); si cambia con il pulsante 🌐 Lingua nella barra dei comandi. La scelta viene salvata e applicata al riavvio, che il programma propone subito (durante un test viene solo memorizzata). Sono tradotti interfaccia, messaggi, eventi e report HTML; restano invariati, per non rompere chi li elabora, le intestazioni e i valori dei CSV (ad esempio la colonna health) e gli stati salvati in summary.json.

Le traduzioni sono file JSON leggibili: il testo italiano scritto nel codice è la chiave, la traduzione il valore ("Avvia test": "Start test"). Per correggere l'inglese o aggiungere una lingua basta un file lang\<codice>.json accanto all'eseguibile (menu 🌐 → Apri la cartella delle traduzioni): i testi mancanti restano in italiano e una traduzione che altera i segnaposto {0} viene ignorata. È lo stesso schema degli altri progetti dello stesso autore (AdbSync, Pietrasanta Traceroute GUI).

SmartScreenL'eseguibile non è firmato digitalmente: al primo avvio Windows può mostrare «PC protetto». Scegliere «Ulteriori informazioni» → «Esegui comunque».

5. Pannello di configurazione

Tutti i valori sono salvati automaticamente all'avvio di ogni test e ripresentati alla successiva apertura del programma. I campi numerici accettano solo numeri interi, salvo le soglie percentuali (che accettano anche la virgola decimale).

5.1 Destinazione

ElementoFunzione e razionale tecnico
Protocollo UDP (RFC 1035): il trasporto normale del DNS, una query per datagramma; è ciò che usa la grande maggioranza dei resolver verso gli autoritativi.
TCP (RFC 7766): obbligatorio per le risposte grandi (troncate in UDP) e per i trasferimenti di zona; un autoritativo deve rispondere anche in TCP.
DoT – DNS over TLS (RFC 7858), porta 853: DNS su connessione TCP cifrata.
DoH – DNS over HTTPS (RFC 8484): DNS dentro richieste HTTPS; usato da browser e sistemi operativi.
DoQ – DNS over QUIC (RFC 9250), porta 853 UDP: cifrato come DoT, ma senza il blocco in testa alla coda di TCP.
Cambiando protocollo, la porta passa al valore standard (53, 853 o 443) se era impostata su uno di questi.
ServerIndirizzo IPv4, IPv6 o nome del server. Il campo è una casella modificabile con cronologia: la freccia mostra gli ultimi 30 valori usati, digitando si ottiene il completamento automatico. Un valore entra in cronologia solo quando viene usato davvero (avvio di un test o verifica riuscita).
Se si indica un nome, viene risolto una sola volta all'avvio con il resolver di sistema e per tutta la sessione si usa quell'indirizzo: la misura riguarda così sempre lo stesso nodo, anche se il nome ne ha diversi.
⋯ (cronologia)Menu per rimuovere dalla cronologia la voce corrente, svuotare la cronologia di quel campo o svuotare tutta la cronologia (server, URL, nomi TLS).
PortaPorta del servizio: 53 per UDP/TCP, 853 per DoT/DoQ.
Famiglia IPUsata solo se il server è indicato per nome. IP automatico preferisce IPv4 se disponibile; Solo IPv4 / Solo IPv6 forzano la famiglia. Utile per confrontare le due raggiungibilità dello stesso server, che spesso hanno percorsi di rete diversi.
URL DoHSolo DoH: URL completo del servizio (es. https://dns.esempio.it/dns-query), con cronologia come il campo Server. Il nome nell'URL è risolto dal sistema a ogni nuova connessione HTTP. Il proxy di sistema è ignorato: la misura deve riguardare il server, non un proxy intermedio.
Metodo POST / GETPOST invia il messaggio DNS nel corpo (application/dns-message); GET lo codifica in base64url nel parametro ?dns=. GET è memorizzabile nelle cache HTTP: per questo l'RFC 8484 raccomanda ID = 0, e il programma usa ID 0 sempre in DoH.
Versione HTTPHTTP/1.1: una richiesta alla volta per connessione. HTTP/2: più richieste contemporanee sulla stessa connessione (multiplexing), è il caso più comune. HTTP/3: HTTP su QUIC (richiede Windows 11 / Server 2022). La versione è esatta: se il server non la supporta la query fallisce invece di ripiegare su un'altra versione, così il test misura ciò che è stato chiesto.
Nome TLS (SNI)Solo DoT e DoQ: nome che il certificato del server deve contenere, inviato nell'estensione SNI. Vuoto = uguale al campo Server. Indispensabile quando il server è indicato per IP ma il certificato riporta un nome. Ha cronologia.
Non verificare il certificatoDisattiva il controllo del certificato (catena, scadenza, nome). Serve solo in laboratorio o con certificati interni: in un test reale un certificato non valido è un problema da segnalare, non da aggirare.
Riusa le connessioniNon presente per UDP. Attivo (predefinito): ogni worker mantiene la propria connessione TCP/TLS/QUIC/HTTP e la riusa, come fa un resolver reale. Disattivo: una nuova connessione per ogni query, quindi la latenza include ogni volta l'handshake (TCP e TLS). Confrontare i due casi misura il costo dell'handshake e la capacità del server di accettare nuove connessioni.
Se il server chiude una connessione inattiva, il programma la riapre in modo trasparente con un solo nuovo tentativo, senza contarlo come errore.

5.2 Query

ElementoFunzione e razionale tecnico
Elenco queryUna query per riga, nella forma nome TIPO (es. dominio.it SOA). Sono accettati anche TIPO nome, il formato CSV nome,TIPO e il solo nome (si usa il tipo predefinito). Le righe vuote e quelle che iniziano con # o ; sono ignorate. I nomi internazionalizzati (con accenti) sono convertiti automaticamente in punycode. Le righe non valide sono scartate con un avviso, visibile negli eventi.
{rnd}Segnaposto sostituito a ogni query da 10 caratteri casuali [a-z0-9], ad esempio {rnd}.dominio.it → k8dm1c75ls.dominio.it. Ogni nome è diverso, quindi nessuna cache intermedia può rispondere: su un autoritativo verifica la generazione delle risposte NXDOMAIN; su un resolver ricorsivo costringe a interrogare gli autoritativi a ogni query. È anche la tecnica degli attacchi «random subdomain» (water torture): usarla con moderazione e solo con autorizzazione.
Carica…Carica l'elenco da un file .txt o .csv (sostituisce il contenuto). Oltre 200.000 righe viene chiesta conferma.
Salva…Salva l'elenco corrente in un file di testo UTF-8. Se l'elenco proviene da un file caricato, propone lo stesso nome con versione incrementata (_v1.0 → _v1.1); altrimenti propone query_<etichetta o server>_v1.0.txt.
Tipo predefinitoTipo di record per le righe senza tipo. Si può scegliere dall'elenco o digitare qualsiasi tipo noto, oppure TYPEnnn / un numero per tipi non in elenco (RFC 3597).
OrdineIn sequenza: le query si susseguono ciclicamente nell'ordine dell'elenco, distribuzione perfettamente uniforme. Casuale: ogni query è estratta a caso; simula meglio un traffico reale ed evita schemi ripetitivi che alcuni meccanismi di rate limiting riconoscono.
Flag RDRecursion Desired. Disattivato (predefinito): come un resolver che interroga un autoritativo; è l'impostazione corretta per testare un autoritativo. Attivato: chiede la risoluzione ricorsiva, indispensabile per testare un resolver. Molti resolver rispondono REFUSED alle query senza RD (protezione dal «cache snooping»). Un autoritativo ben configurato, invece, risponde solo per le proprie zone anche con RD attivo: se risolvesse nomi di terzi sarebbe un open resolver, sfruttabile per attacchi di amplificazione.
EDNS0 + bufferAggiunge il record OPT (RFC 6891) e annuncia la dimensione massima di risposta UDP accettata. Il valore consigliato è 1232 byte (DNS Flag Day 2020): evita la frammentazione IP, causa frequente di risposte perse. Senza EDNS le risposte UDP sono limitate a 512 byte e quelle più grandi arrivano troncate (flag TC). Con EDNS il programma interpreta anche l'RCODE esteso e gli Extended DNS Error.
DNSSEC (DO)Imposta il bit DNSSEC OK: il server include le firme (RRSIG) nelle risposte delle zone firmate. Le risposte diventano molto più grandi: è un buon test di carico per banda e frammentazione, e verifica che il server serva correttamente i record DNSSEC.

5.3 Carico e durata

ElementoFunzione e razionale tecnico
QPS obiettivoQuery al secondo complessive da inviare. Le query sono distribuite in modo regolare su una griglia temporale assoluta (query n all'istante n/QPS), non a raffiche. 0 = nessun limite: ogni worker invia la query successiva appena riceve la risposta (prova di massimo throughput, da usare con estrema cautela verso server esterni).
WorkerNumero di query contemporaneamente «in volo» (da 1 a 5000). Ogni worker ha un solo canale (socket o connessione) e una sola query alla volta. Per la legge di Little servono almeno QPS × latenza media worker per sostenere il ritmo in condizioni normali, ma per mantenerlo anche quando il server non risponde (ogni query attende il timeout) ne servono QPS × timeout. Esempio: 200 qps con timeout di 2 s → 400 worker. Con meno worker, durante un'interruzione il carico inviato cala da solo (si vede nella linea «Inviate/s»): il riquadro Avvisi lo segnala.
Timeout (ms)Attesa massima di una risposta (da 50 a 60.000 ms), oltre la quale la query è contata come TIMEOUT. I resolver reali attendono tipicamente da 400 ms a 2 s prima di riprovare o passare a un altro name server: un valore in questa fascia rende il test realistico. Una query in timeout è conteggiata nel secondo in cui il timeout scade.
Rampa (s)Durata della salita graduale: il ritmo cresce linearmente da zero al QPS obiettivo. Evita di colpire il server con il carico pieno a freddo (cache, connessioni, eventuali sistemi anti-DDoS) e permette di osservare a quale livello iniziano i problemi.
DurataGiorni, ore e minuti. Allo scadere il test si arresta in modo ordinato e genera il report.
Senza limite di durataIl test prosegue finché non si preme Arresta o si chiude il programma.
Perché una griglia temporale fissaSe il programma è in ritardo (server lento o worker insufficienti), le query non inviate in tempo non vengono recuperate con una raffica: oltre 1 secondo di ritardo la griglia viene riallineata. Una raffica di recupero falserebbe la misura nel momento peggiore. Il ritardo diventa invece visibile: la linea «Inviate/s» scende sotto l'obiettivo. È il comportamento che evita l'errore metodologico noto come coordinated omission.

5.4 Valutazione dello stato del server

Ogni secondo il programma valuta le query completate in una finestra mobile e assegna uno stato. Gli stessi criteri alimentano l'indicatore «Stato server», la striscia colorata del report, la colonna health degli aggregati e gli eventi.

ElementoFunzione
Finestra di osservazione (s)Numero di secondi considerati (da 1 a 300, predefinito 10). Finestre brevi reagiscono subito ma sono «nervose»; finestre lunghe sono stabili ma segnalano più tardi.
Degradato se successo sotto (%)Predefinito 99%: più di 1 query su 100 senza risposta valida nella finestra porta lo stato a DEGRADATO.
… oppure p95 oltre (ms)Predefinito 500 ms: anche con tutte le risposte, se il 5% più lento supera la soglia lo stato è DEGRADATO. Le risposte lente equivalgono quasi a risposte perse, perché i resolver vanno in timeout e ritentano.
Non disponibile se successo sotto (%)Predefinito 50%. Lo stato è NON DISPONIBILE anche quando nella finestra sono state inviate query e non ne è stata completata nessuna. Deve essere inferiore alla soglia di degrado.
NXDOMAIN validoSe attivo (predefinito), NXDOMAIN è una risposta corretta: il server ha risposto che il nome non esiste, ed è la risposta attesa per le query {rnd}. Disattivarlo solo se tutti i nomi dell'elenco devono esistere.
IsteresiIl peggioramento è segnalato subito; il miglioramento solo dopo che il nuovo stato è rimasto stabile per tanti secondi quanti sono quelli della finestra. Così un singolo secondo buono durante un'interruzione non produce una raffica di eventi OK/NON DISPONIBILE alternati. Un episodio è contato ogni volta che si passa da OK (o nessun dato) a DEGRADATO o NON DISPONIBILE.

«Successo» significa risposta NOERROR (comprese le risposte senza record, dette NODATA), più NXDOMAIN se l'opzione è attiva. SERVFAIL, REFUSED, gli altri RCODE, i timeout e gli errori di trasporto sono fallimenti.

5.5 Log ed export

ElementoFunzione e razionale tecnico
CartellaCartella in cui viene creata una sottocartella per ogni sessione, con nome AAAAMMGG_hhmmss_PROTOCOLLO_server[_etichetta]. Il pulsante «…» apre la selezione.
Etichetta sessioneTesto facoltativo aggiunto al nome della cartella (cliente, ticket, scenario). Facilita il riordino di molte sessioni.
Log per queryTutte le query: una riga per ogni query (massimo dettaglio forense). Solo fallimenti: registra solo timeout, errori e risposte non valide; adatto ai test di più giorni ad alto ritmo. Disattivato: solo aggregati ed eventi. In tutti i casi gli aggregati al secondo e al minuto restano completi.
Rotazione file (MB)Dimensione oltre la quale il log per query passa a un nuovo file (queries_0001.csv, queries_0002.csv, …). File di qualche centinaio di MB restano gestibili con Excel, editor e strumenti di analisi.
Formato CSVExcel italiano: separatore ; e virgola decimale, si apre con un doppio clic in Excel configurato in italiano. Standard: separatore , e punto decimale (RFC 4180), per Python, Power BI, SIEM. Il formato vale per tutti i CSV della sessione ed è registrato in session.json, così il report li rilegge correttamente.

Lo spazio del log per query è di circa 110 byte per query: ad esempio 100 qps per 7 giorni ≈ 6,7 GB.

5.6 Avvisi

Il riquadro giallo in fondo alla configurazione si aggiorna mentre si modificano i valori e segnala situazioni non bloccanti ma importanti:

  • Worker insufficienti: con il numero di worker indicato, se il server smette di rispondere il carico scenderebbe a circa worker ÷ timeout qps. È indicato il numero minimo per mantenere l'obiettivo.
  • QPS illimitato: promemoria sull'uso responsabile.
  • Spazio su disco: stima del log per query oltre i 2 GB.
  • Certificato non verificato.

Gli stessi avvisi compaiono nella finestra di conferma dell'avvio.

Perché la percentuale di AAIl flag AA (Authoritative Answer) dice che la risposta viene dal server titolare della zona e non da una cache. Testando un autoritativo deve essere vicino al 100%: un valore basso indica che si stanno interrogando nomi di zone che il server non ospita, o che si sta interrogando un resolver.

9. Metodologia di misura

Generazione del carico

  • Worker: ciascuno ha un proprio canale (socket UDP «connesso», connessione TCP/TLS, connessione QUIC o client HTTP condiviso per DoH) e una query alla volta. Questo isola i worker tra loro e rende la concorrenza esattamente quella configurata.
  • Scheduler: istante di invio della query n = n / QPS dall'inizio (con la rampa, una curva che fa crescere il ritmo linearmente). Se l'invio è in ritardo di oltre 1 s la griglia viene riallineata invece di recuperare con una raffica.
  • Durante il test Windows non va in sospensione automatica e la risoluzione del timer di sistema è portata a 1 ms, per una cadenza regolare anche a pochi qps.

Costruzione e validazione delle query

  • ID casuale per ogni query in UDP, TCP e DoT; ID 0 in DoH e DoQ, come richiesto dagli RFC 8484 e 9250.
  • Classe IN; flag RD secondo configurazione (CD sempre a 0); record OPT se EDNS è attivo (buffer e bit DO configurabili).
  • Una risposta è accettata solo se ha il bit QR, lo stesso ID e la stessa sezione domanda della query (confronto senza distinzione tra maiuscole e minuscole). È la stessa verifica che fa un resolver per difendersi dalle risposte contraffatte: garantisce che ogni risposta conteggiata sia davvero quella della query misurata.
  • In UDP le risposte con ID diverso sono scartate e si continua ad attendere quella giusta fino al timeout (risposte tardive).
  • In TCP/DoT, dopo un timeout la connessione viene chiusa e riaperta (lo stato del flusso non è più affidabile).
  • In DoQ ogni query usa un nuovo stream bidirezionale sulla connessione QUIC del worker (ALPN doq, inattività massima 30 s).

Misura della latenza

  • Cronometro ad alta risoluzione avviato subito prima dell'invio e fermato alla ricezione completa della risposta.
  • Se per quella query è necessario aprire una connessione (primo invio di un worker, connessione chiusa dal server, riuso disattivato), la latenza include l'handshake TCP/TLS/QUIC, come accade a un client reale.
  • Le latenze sono raccolte in un istogramma log-lineare: risoluzione di 1 µs fino a 64 µs, poi 32 intervalli per ogni raddoppio, con errore relativo massimo intorno al 3% su tutta la scala fino a decine di secondi. I percentili di secondo, minuto, finestra e sessione sono calcolati dall'istogramma dell'insieme corrispondente.

Aggregazione

  • Ogni risultato è attribuito al secondo in cui la query si conclude. Ogni secondo chiuso produce una riga in intervals_1s.csv; ogni 60 secondi una riga in intervals_1m.csv.
  • Le statistiche sono elaborate da un unico thread dedicato, separato dai worker: il percorso di invio non ha lock e la misura non è disturbata dall'elaborazione.
  • Se il PC resta bloccato o sospeso per più di un'ora, l'intervallo mancante non viene riempito di secondi vuoti: è registrato un evento di «salto temporale».

12. Scenari di test consigliati

Server autoritativo

  1. Ricognizione. Individuare i name server della zona (record NS) e i loro indirizzi. Verificare se sono su reti diverse: l'RFC 2182 raccomanda di distribuirli, perché un guasto di rete non li colpisca tutti insieme.
  2. Coerenza. Con «Verifica destinazione», interrogare zona SOA su ciascun name server: il numero di serie deve coincidere, altrimenti i secondari non si sincronizzano. Confrontare anche NS, MX e i record principali.
  3. Protocolli. Ripetere la verifica in TCP (deve funzionare), senza EDNS (risposte limitate a 512 byte, possibile TC) e con DNSSEC (DO) se la zona è firmata.
  4. Disponibilità nel tempo. Elenco con soli nomi delle zone ospitate più {rnd}.zona A, flag RD disattivato, carico basso (2–20 qps), durata 24–72 ore. Per confrontare più name server, avviare più istanze del programma in parallelo, una per server: si vede subito se i degradi sono comuni (rete condivisa) o di un solo nodo.
  5. Capacità a gradini (solo con autorizzazione formale). Sessioni di 10 minuti a carico crescente (es. 10, 50, 100, 200 qps) con rampa. Annotare il livello al quale salgono p95/p99 o compaiono timeout e risposte troncate.

Resolver ricorsivo

  • Flag RD attivo, elenco di domini reali con ordine casuale, NXDOMAIN valido.
  • Il primo giro riempie la cache: da lì in poi le latenze misurano soprattutto le risposte dalla cache. Per misurare la risoluzione completa usare nomi {rnd} (con moderazione: ognuno genera traffico verso gli autoritativi di quel dominio).

Servizi cifrati (DoT, DoH, DoQ)

  • Confrontare riuso delle connessioni attivo e disattivo per misurare il costo dell'handshake e la capacità di accettare nuove connessioni.
  • In DoH confrontare HTTP/1.1, HTTP/2 e HTTP/3 e i metodi GET e POST.

13. Come leggere i risultati

Cosa si osservaInterpretazione probabile

Risposte/s sotto Inviate/s, timeout in aumentoIl server (o la rete) perde query. Se succede oltre una certa soglia di carico ed è proporzionale al carico, è un limite di capacità o un meccanismo di rate limiting.
Timeout a picchi regolari (ogni N minuti)Attività periodiche sul server o sulla rete: ricaricamento delle zone, backup, rotazione dei log, cambi di percorso. Confrontare gli orari con i log del server.
p50 stabile, p95/p99 a picchiCode momentanee sul server o jitter di rete. Se i picchi coincidono con quelli di più name server su reti diverse, la causa è probabilmente vicino alla postazione di prova.
Tutte le latenze salgono insiemeSaturazione (CPU, banda, coda di rete) o cambio di percorso di rete.

14. Limiti e avvertenze

  • Un solo indirizzo sorgente. Tutto il traffico parte dalla postazione di prova. Le protezioni per indirizzo IP (RRL, firewall, anti-DDoS) intervengono molto prima della reale capacità del server: il limite misurato da un solo PC è spesso quello della protezione. Per la capacità reale servono più postazioni o un test concordato con il gestore.
  • La misura include la rete. Latenze e perdite comprendono il percorso tra la postazione e il server. Per distinguere problemi del server da problemi di rete, confrontare più name server e, se possibile, più punti di misura.
  • Anycast. Se il server è anycast, si misura il nodo raggiunto dalla postazione di prova, non l'intero servizio.
  • Capacità del PC di prova. A ritmi molto alti (migliaia di qps) il limite può diventare la CPU o la rete del PC: controllare «Inviate/s» e la «coda» nella barra di stato.
  • Risoluzione del nome. Il nome del server è risolto una volta all'avvio: un cambio di indirizzo durante il test non viene seguito.
  • Aggiornamenti di Windows. Il programma impedisce la sospensione, ma non i riavvii pianificati: disattivarli per la durata dei test lunghi.

15. Risoluzione dei problemi

SintomoCausa e rimedio
Tutte le risposte REFUSEDResolver interrogato senza RD → attivare «Flag RD». Autoritativo interrogato per zone che non ospita → usare nomi delle sue zone. REFUSED anche con RD attivo → indirizzo sorgente non autorizzato (ACL).
Tutte le query in TIMEOUTPorta filtrata da un firewall (locale, aziendale o del server), indirizzo errato, protocollo non offerto (es. DoT non attivo). Provare UDP e TCP sulla 53 per confronto.
NET_ERROR «ConnectionReset» in UDPIl server ha risposto «porta non raggiungibile» (ICMP): nessun servizio DNS su quell'indirizzo e porta.
TLS_ERRORCertificato non attendibile o con nome diverso: impostare il «Nome TLS (SNI)» corretto. Solo in laboratorio, disattivare la verifica.
HTTP_ERROR 404/415 in DoHPercorso dell'URL errato (spesso /dns-query) o metodo non supportato: provare l'altro metodo.
«QUIC non supportato»DoQ e HTTP/3 richiedono Windows 11 o Windows Server 2022 o successivi e msquic.dll accanto all'eseguibile.
Molte «risposte tardive»Timeout troppo corto rispetto alla latenza reale del server: aumentarlo.
Coda in crescita nella barra di statoIl PC non elabora i risultati al ritmo richiesto: ridurre il QPS o il log per query («Solo fallimenti»).
Errore imprevisto dell'interfacciaIl test continua e i dati restano salvati. Inviare il file crash.log della cartella dati per la diagnosi.

17. Glossario

TermineDefinizione
AAAuthoritative Answer: la risposta proviene dal server titolare della zona.
AnycastStesso indirizzo IP annunciato da più nodi: si raggiunge il più vicino in termini di rete.
AutoritativoServer che ospita le zone e ne fornisce i dati originali.
EDEExtended DNS Error (RFC 8914): codice che spiega il motivo di un errore.
EDNS0Estensione del DNS (RFC 6891) per risposte UDP oltre 512 byte, flag aggiuntivi e opzioni.
NODATANOERROR senza record: il nome esiste ma non ha record del tipo chiesto.
Open resolverServer che risolve nomi di terzi per chiunque: sfruttabile per attacchi di amplificazione.
Percentilep95 = valore sotto il quale cade il 95% delle misure.
QPSQuery al secondo.
RD / RARecursion Desired (chiesta dal client) / Recursion Available (offerta dal server).
Resolver ricorsivoServer che risolve qualsiasi nome interrogando gli autoritativi e conservando le risposte in cache.
RRLResponse Rate Limiting: limitazione delle risposte per indirizzo sorgente sugli autoritativi.
SNI / ALPNEstensioni TLS: nome del server richiesto / protocollo applicativo (es. doq).
SOA serialNumero di versione della zona: deve coincidere su tutti i name server.
TCTruncated: risposta troppo grande per UDP; il client dovrebbe ripetere la query in TCP.
